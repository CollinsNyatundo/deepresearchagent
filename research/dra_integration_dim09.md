# Dimension 09: Hierarchical LaTeX Composition (IHDS)

## Overview

This dimension investigates the feasibility of integrating AI-Researcher's Iterative Hierarchical Document Synthesis (IHDS) into DRA. It covers section-specific composers, LaTeX generation pipeline, and the effort required for publishable-grade output.

---

## Key Findings

### 1. IHDS is Extremely Complex and Not Well-Documented

**Claim:** The AI-Researcher paper (NeurIPS 2025 Spotlight) describes IHDS at a high level, but the actual implementation details are not publicly available in sufficient detail for direct porting.[^1]

**Source:** AI-Researcher GitHub README

**URL:** https://github.com/HKUDS/AI-Researcher

**Date:** 2025

**Excerpt:**
> "Automatically generates polished, full-length academic papers."

**Context:** The DRA plan's IHDS description is based on the NeurIPS paper and conceptual design, not on reading the actual source code. The plan proposes 5+ section-specific composers (IntroductionComposer, RelatedWorkComposer, ExperimentsComposer, ConclusionComposer, AbstractComposer) with strict structural requirements. Implementing this from scratch would require:
- Deep understanding of academic paper structure across disciplines
- LaTeX generation expertise
- BibTeX management
- Figure generation and placement
- Citation style handling (APA, IEEE, ACM, etc.)

This is a research-level feature, not a P1-P2 implementation task.

**Confidence:** High

---

### 2. LaTeX Generation is a Hard Problem

**Claim:** Generating valid LaTeX programmatically is difficult because LaTeX is a macro expansion language with complex state. Small errors (missing braces, undefined commands) cause compilation failures that are hard to debug programmatically.[^2]

**Source:** LaTeX Community Knowledge

**URL:** https://www.latex-project.org/

**Date:** 2026

**Excerpt:** N/A (general knowledge)

**Context:** The DRA plan proposes generating LaTeX source with `SectionComposer` subclasses. For this to work:
- Each composer must generate syntactically valid LaTeX
- Cross-references must be resolved (\ref, \cite)
- Bibliography must be generated in correct format
- Figures must be generated and placed correctly
- Table of contents must be accurate

A single syntax error (e.g., a `#` character not escaped as `\#`) breaks the entire document. This requires robust escaping and validation, which the plan does not address.

**Confidence:** High

## Tensions and Counter-Arguments

### Tension 1: Academic Aspirations vs. Practical Value

The DRA plan is ambitious about academic-grade output ("publishable-grade academic research platform"). However, the primary use case for DRA is web research for developers, founders, and indie hackers — not academic paper submission.

**Counter-argument:** If academic users want LaTeX, they can export Markdown and convert via Pandoc. DRA should focus on making the Markdown output as high-quality as possible, rather than adding LaTeX complexity.

### Tension 2: IHDS Effort vs. Other Features

Implementing IHDS would require:
- 5+ section-specific composer classes
- LaTeX template system
- BibTeX generation and management
- Figure generation pipeline
- Citation style engine
- LaTeX validation and error recovery

Estimated effort: 4-8 weeks for a basic implementation, 12+ weeks for a robust one. This is more than the entire P0+P1+P2 effort combined.

**Counter-argument:** Defer IHDS indefinitely. If users request LaTeX, provide a simple Markdown→LaTeX converter (via Pandoc or Jinja2 templates) rather than a full IHDS pipeline.

### Tension 3: Maintenance Burden

LaTeX templates break when:
- LaTeX distributions update (TeX Live annual releases)
- Packages change (syntax changes, deprecation)
- Journal requirements change (different templates, formats)
- Unicode characters are not supported by all fonts

**Counter-argument:** Markdown does not have these problems. It's stable, portable, and widely supported. DRA should invest in Markdown quality, not LaTeX complexity.

## Recommendations

### 1. Remove IHDS from the Integration Plan

The IHDS feature is not aligned with DRA's core value proposition and requires disproportionate effort. Replace with:

```python
# Simple Markdown → LaTeX converter (if user requests LaTeX)
async def export_latex(report: str, citations: list) -> str:
    template = jinja2.Template(LATEX_TEMPLATE)
    bibtex = generate_bibtex(citations)
    return template.render(report=report, bibtex=bibtex)
```

### 2. Enhance Markdown Export Instead

Add features to the existing Markdown export:
- YAML frontmatter with metadata (title, date, query, model)
- Table of contents generation
- Citation links (clickable URLs)
- Footnotes
- Mermaid diagrams for mindmaps
- Better code block formatting

### 3. If LaTeX is Needed, Use Pandoc

```python
async def export_latex(report: str) -> str:
    """Generate LaTeX source via Pandoc (if installed)."""
    if shutil.which("pandoc"):
        return await pandoc_convert(report, "latex")
    else:
        # Fallback: simple Jinja2 template
        return jinja2_latex_convert(report)
```

This provides LaTeX for users who need it, without requiring DRA to manage LaTeX compilation.
